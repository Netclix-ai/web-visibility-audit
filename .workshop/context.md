## Async audit execution (critical architecture — Sept 2026)
- Audit creation is now ASYNC everywhere: `POST /api/audits`, `POST /api/websites/{id}/audits/rerun`, `POST /api/widget/audit`, and `POST /api/integrations/ghl/audit-request` all return fast with `status:"running"` (or, for the GHL "lite" route, already-completed since lite is fast enough to run inline). The heavy full-audit crawl (JS render + sequential PSI calls, up to ~2 min worst case) runs in a background daemon thread (`audit_engine.engine.execute_audit`, opens its own DB session via `session_scope()`).
- `audit_engine/engine.py`: `create_audit_stub(db, website, depth="full")` — fast synchronous part (creates Audit row, status="running", stores `depth`). `execute_audit(audit_id)` — the heavy pipeline, reads `audit.depth` and passes it to `live_collector.collect()`; meant to run in a background thread for `depth="full"`, but can be called inline for `depth="lite"` since it's fast (~1-5s). `run_audit(db, website, depth="full")` still exists as a synchronous convenience wrapper for scripts/tests only.
- `routes.py`: `_run_audit_in_background(audit_id)` spawns the daemon thread for internal create/rerun/widget. The GHL route calls `execute_audit()` directly (no thread) since lite mode is fast enough to run inline within the request.

## Audit "depth": full vs lite (Sept 2026 — added for GHL bulk scoring)
- `Audit.depth` column: `"full"` (default) or `"lite"`.
- `live_collector.collect(url, business_name=None, location=None, depth="full")`: `depth="lite"` skips (a) the Playwright JS-render pass entirely (sets `js_render_failed=True` so the 6 DOM-dependent checks in `live_checks.py` degrade to their pre-existing NOT_APPLICABLE path, same as a real render failure) and (b) both PageSpeed Insights calls (mobile+desktop) — `pagespeed_mobile`/`pagespeed_desktop` stay `None`, so `live_checks.py`'s `_perf_score_check` degrades Performance checks to NOT_APPLICABLE via its existing "score is None" branch. **No changes were needed in `live_checks.py` or `scoring.py`** — both already had graceful NOT_APPLICABLE degradation paths that lite mode just deliberately triggers. Everything else (raw HTML fetch, headers, robots.txt/sitemap, DNS SPF/DMARC, Google Places lookup for NAP) still runs in lite mode, so on-page/technical/local-SEO checks are still real, unaffected data.
- Lite mode exists specifically so bulk/outreach scoring (GHL, future CSV import, etc.) can run hundreds/thousands of audits cheaply and fast (~1-5s each, no Browserless usage, no PSI quota burned) — full mode remains the default for anyone actually viewing/requesting a report.
- Verified via live test: a lite audit against example.com completed end-to-end in ~3s with `overall_score=70.2`, `overall_grade="C-"`, and Performance-category checks correctly `NOT_APPLICABLE`.

## GoHighLevel (GHL) integration — round-trip stays entirely inside GHL, no GHL API key needed
- Endpoint: `POST /api/integrations/ghl/audit-request` (routes.py, `GHLAuditRequest` pydantic model: `contact_id`, `website` (required), `business_name`, `location`, `first_name`, `last_name`, `email`, `phone` optional).
- Flow: **GHL Workflow #1** (trigger = e.g. contact tagged "needs-audit" or added to a list of up to thousands of contacts) → "Custom Webhook" outbound action → POSTs contact fields to our endpoint above. Our app runs a `depth="lite"` audit synchronously (fast), builds a prospect `Report`/share_token, then POSTs the result (`ghl_client.post_audit_result()`) to a GHL **Inbound Webhook Trigger URL** (this is **GHL Workflow #2**'s trigger — the URL is generated inside GHL's Workflow Builder when you add an "Inbound Webhook" trigger and copy its URL). Workflow #2 then uses GHL's own native "Update Contact" action (no API key required — GHL maps the inbound webhook payload's fields directly onto that contact's custom fields) followed by a native SMS/Email action merging those custom fields into the outreach message. **This means the ~5,000-10,000-contact bulk case the user wants is just: add all those contacts to Workflow #1's trigger list/tag in GHL — no CSV export/import, no script on our side.**
- `ghl_client.py` (new file, project root): `post_audit_result(payload: dict) -> bool` — the only outbound call this app makes to GHL; POSTs to `GHL_RESULTS_WEBHOOK_URL` (project secret, = the Inbound Webhook Trigger URL from GHL Workflow #2). Never raises; returns False and logs if the URL isn't set yet or the POST fails, so Workflow #1 can be tested/wired up before Workflow #2 exists.
- Auth on the inbound side: `GHL_INBOUND_SECRET` (project secret, a value we generate — not something GHL issues) checked against the `X-GHL-Secret` header, which the user must configure as a static header in GHL Workflow #1's Custom Webhook action config. If `GHL_INBOUND_SECRET` isn't set, the check is skipped (useful for initial wiring/testing).
- Idempotency: `Business.ghl_contact_id` (new column) — repeat calls for the same GHL contact_id reuse/update the same Business row (update name/contact fields) rather than creating duplicates, but each call still creates a fresh Website+Audit (so score history accumulates over repeat runs, e.g. re-entering the workflow later).
- **No GHL API key/Private Integration Token is needed for this flow** — both directions are plain webhooks GHL's Workflow Builder already supports natively (outbound Custom Webhook action; inbound Webhook Trigger + native Update Contact action). A GHL API key would only become relevant for a *different*, not-yet-built feature: our app proactively pulling/paginating a contact list via GHL's REST API (not needed since the user chose the "workflow fires one webhook per contact" approach for even their large 5-10k backlog, by just adding them all to Workflow #1's trigger).
- Verified end-to-end in the dev sandbox: POSTed a test payload to `/api/integrations/ghl/audit-request`, got a real completed lite audit back in ~3.1s (score 70.2, grade C-, working prospect report_url), confirmed idempotent Business reuse on a second call with the same `contact_id`, and confirmed Performance-category checks were correctly `NOT_APPLICABLE` (no PSI/Browserless cost incurred). `GHL_RESULTS_WEBHOOK_URL` and `GHL_INBOUND_SECRET` are not yet set (pending user setting up GHL Workflow #2 and choosing a secret value) — until then, the endpoint works and returns results in its own HTTP response, but the automatic hand-back POST to GHL silently no-ops (logged only).
- **Still pending / next steps for the user**: (1) create custom fields in GHL for score/grade/report link (e.g. `visibility_score`, `visibility_grade`, `visibility_report_url`) if they don't already exist, (2) build GHL Workflow #2 with an Inbound Webhook trigger, copy its URL into the `GHL_RESULTS_WEBHOOK_URL` project secret, (3) pick any secret string, add it as the `GHL_INBOUND_SECRET` project secret, and configure that same value as a static header (`X-GHL-Secret`) on Workflow #1's Custom Webhook action, (4) build Workflow #1 (trigger = tag/list, action = Custom Webhook POST to `https://<published-app-domain>/api/integrations/ghl/audit-request` with contact fields mapped into the JSON body shown above).

## Playwright rendering pipeline (audit_engine) — THREE-TIER fallback as of Sept 2026
`audit_engine/browser_worker.py`'s `_launch_browser(p)` now tries, in order:
1. **Local Playwright Chromium launch** (`p.chromium.launch()`) — the fast/normal path, works fine in the sandbox dev server which has all required OS libs and runs `start.sh`'s `playwright install chromium` step.
2. **Self-heal binary download**: if launch fails with "Executable doesn't exist" (nothing has ever downloaded the browser binary at this path), calls `_ensure_browsers_installed()` — runs `python -m playwright install chromium` via subprocess (one-shot flag), then retries launch. This fixes the "binary was never downloaded" case but NOT missing OS-level shared libraries.
3. **Remote Browserless.io fallback**: if local launch still fails after retries + self-heal (e.g. the published/production container's base OS image is missing shared libs like `libglib-2.0.so.0` that Chromium needs to actually execute — confirmed via `fetch_deployment_logs` showing `error while loading shared libraries: libglib-2.0.so.0: cannot open shared object file` — this is NOT fixable by `playwright install`, which only downloads the browser binary, not OS packages, and there's no root/apt access in this container), `_connect_remote_browser(p)` connects to a hosted Chromium via `p.chromium.connect_over_cdp(f"wss://production-sfo.browserless.io?token={BROWSERLESS_API_KEY}")`. Returns a normal Playwright `Browser` object — every other line of code (`.new_context()`, `.new_page()`, `.goto()`, `wait_for_function` content-polling, etc.) is unchanged and works identically whether the browser is local or remote.
- `BROWSERLESS_API_KEY` is a project secret. When unset, `_connect_remote_browser()` returns `None` immediately (no error) and the original raise-last-error behavior is preserved — this fallback is additive/optional, never required for the sandbox dev server. Note: `depth="lite"` audits never invoke Playwright/Browserless at all (skipped entirely, see above), so this fallback chain only matters for `depth="full"` audits.
- `audit_engine/live_collector.py`'s `_render_and_verify()` is the render entry point, calling `browser_worker.render_page()`. Key lesson #1: a Playwright render can report "success" (no exception) while the page's own JS hasn't finished injecting content yet — verify by content (word count / H1 presence), not just absence of exceptions. Key lesson #2: do NOT use `networkidle` as a retry/escalation tactic — many real sites (analytics beacons, chat widgets, long-poll/websocket) never go network-idle. Fixed via **direct DOM content polling**: `page.wait_for_function("document.body.innerText.trim().length > 40", timeout=content_wait_ms)` — returns the instant real content appears while still enforcing a hard ceiling. Attempt schedule (wait_until, timeout_ms, content_wait_ms): `[("load",20000,4000), ("load",20000,10000), ("load",25000,20000)]` — no `networkidle` anywhere.
- `_looks_like_thin_spa_shell()` flags near-empty SPA mount points (React/Vue/Next/Gatsby) for extra content-verification scrutiny; genuinely sparse static pages are trusted after one successful render.
- `live_checks.py`'s `render_uncertain` flag (from `profile["js_render_failed"]`) guards 6 DOM-dependent checks (h1_tag, heading_structure, keyword_consistency, content_length, image_alt_text, internal_linking) — reports honest `NOT_APPLICABLE`/"Could not verify" instead of false FAIL when rendering couldn't be verified (this is the same flag `depth="lite"` deliberately sets).
- Test ad-hoc renders via `PLAYWRIGHT_BROWSERS_PATH="$(pwd)/.playwright-browsers" uv run python3 -c "from audit_engine import browser_worker; ..."` (must set this env var manually to match what start.sh does for the real dev server).
- Always check whether the server that generated a failing audit was running current code (uvicorn --reload picks up changes, but confirm via audit's `created_at` vs. file mtimes) before assuming a fix didn't work.

## CRITICAL — dev sandbox vs published/live deployment are DIFFERENT environments
- `start.sh` sets `PLAYWRIGHT_BROWSERS_PATH` to a project-local dir and runs `playwright install chromium` — but this ONLY happens in the sandbox dev server. The published deployment does NOT run `start.sh` (`.workshop/deploy.json` schema only supports `backend.{root,entry,runner}` and optional `frontend.{root,dist,install,build}` — no hook for arbitrary setup commands). `.workshop/deploy.json` now exists: `{"backend": {"root": ".", "entry": "app:asgi", "runner": "uvicorn"}}`.
- Production's base container OS image is missing shared libraries Chromium needs (confirmed: `libglib-2.0.so.0` missing, likely more behind it) — this is a platform/image constraint, not fixable via pip/uv/pyproject.toml or any Python-level self-heal. Consulted the oracle on this specifically; conclusion: no pure-Python or pip-installable fix exists for missing OS shared-library dependencies of a native binary like Chromium. The only reliable fixes are (a) run the browser somewhere that already has the right OS libs (a remote browser service — what we did, via Browserless.io), or (b) get control over the production container's base image (not available to us here).
- **When diagnosing "audit looks broken only in production" reports**: check `fetch_deployment_logs` for `Executable doesn't exist` (binary never downloaded — should now self-heal), `error while loading shared libraries` (OS lib missing — should now fall back to Browserless), `Exception in thread browser-worker`, `[browser_worker] timed out waiting for worker thread`. If Browserless fallback itself is failing, check `BROWSERLESS_API_KEY` is set and check Browserless dashboard for quota/plan limits.
- When a user reports a failure and the local DB/dev server shows no corresponding bad data, **always check `fetch_deployment_logs` before concluding the report doesn't reproduce** — they may be testing the published app. Dev sandbox and production share the SAME Neon database (single `DATABASE_URL`), so DB queries alone can't distinguish which environment produced a given row — must cross-reference with deployment logs / timestamps.

## Email delivery (Resend) — sandbox restriction, not a bug
- `emailer.py` uses Resend's shared `onboarding@resend.dev` sending domain (unverified). **Confirmed directly against the live Resend API and in production logs**: in this mode, Resend hard-blocks delivery to any recipient except the account owner's own verified address (`dev@netclixmarketing.com`) — every other address gets a `ResendError` ("You can only send testing emails to your own email address...") which `send_email()` catches/logs (never raises) but means lead-facing emails silently never arrive, while the agency notification email always succeeds.

No code change needed — `send_email()` already accepts `from_email` and both call sites already pass `b_dict.get("from_email")` through. Status: pending, user has not yet verified a domain.

## Category removal precedent: "Authority" (Sept 2026)
- The "Links / Authority" category (backlinks, referring domains, anchor text, nofollow ratio — always NOT_APPLICABLE, no backlink data source connected) was fully removed as not being an on-site feature. Pattern followed for any future category removal: (1) remove the check-generation code in `live_checks.py`, (2) in `seed.py`, remove from `CATEGORIES` and redistribute its weight proportionally across the rest, add a one-time idempotent migration (`_migrate_remove_authority`-style) that deactivates (not deletes) the old category's `ScoringConfig` row — kept for historical audits' FK integrity — and reweights/re-sorts the remaining active categories for existing installs, (3) remove display-name/finding-template entries in `recommendations.py`/`report_builder.py`, (4) update any hardcoded category-count copy in frontend files (search for "8 categories"/"eight categories" etc.), (5) filter `/api/settings/scoring` to `active=True` only so retired categories vanish from the admin weights UI. `scoring.py` needed **zero changes** — it already only scores/normalizes over categories actually present in a given audit's checks, and already excludes `None`-score categories from the overall weighted average.
